# Lumora — План разработки

## Общие правила

Перед написанием любого кода необходимо:

- изучить текущую архитектуру проекта;
- не ломать существующий функционал;
- соблюдать принятый стиль кода;
- писать понятный, поддерживаемый и масштабируемый код;
- использовать современные практики разработки;
- разделять бизнес-логику, инфраструктуру и API;
- после завершения каждой задачи обновлять документацию.

---

# Этап 1. Инициализация проекта

## Цель

Подготовить основу проекта.

### Необходимо

- Создать структуру проекта.
- Настроить Go-модуль.
- Подключить Docker.
- Настроить docker-compose.
- Подключить PostgreSQL.
- Подключить Redis.
- Настроить систему конфигурации через `.env`.
- Настроить логирование.
- Настроить graceful shutdown.
- Добавить health-check.

### Результат

Проект запускается одной командой.

---

# Этап 2. Авторизация

## Необходимо

Реализовать систему пользователей.

### Возможности

- Регистрация
- Авторизация
- JWT
- Refresh Token
- Выход
- Получение профиля

---

# Этап 3. Пользователь

Реализовать профиль пользователя.

Поля:

- имя
- страна
- язык
- профессия
- интересы
- изучаемые темы

Добавить возможность редактирования профиля.

---

# Этап 4. Контекст пользователя

Создать механизм хранения контекста.

Контекст должен использоваться AI при генерации брифинга.

Необходимо предусмотреть возможность изменения контекста пользователем в любой момент.

---

# Этап 5. Источники информации

Реализовать систему подключения источников.

Поддерживаемые источники MVP:

- RSS
- YouTube
- Telegram

Каждый источник должен храниться отдельно.

---

# Этап 6. Импорт данных

Создать сервис, который:

- получает новые публикации;
- сохраняет их;
- исключает дубликаты;
- подготавливает текст к обработке.

---

# Этап 7. Обработка событий

Реализовать pipeline обработки.

Этапы:

1. Очистка текста.
2. Дедупликация.
3. Кластеризация.
4. Определение темы.
5. Определение важности.
6. Формирование общего события.

---

# Этап 8. AI

Для каждого события необходимо сгенерировать:

- что произошло;
- почему произошло;
- что изменилось;
- что это значит лично для пользователя.

При генерации использовать пользовательский контекст.

---

# Этап 9. Генерация брифинга

Создать механизм формирования:

- утреннего брифинга;
- вечернего брифинга.

Брифинг должен содержать только наиболее важные события.

---

# Этап 10. Push-уведомления

Реализовать систему уведомлений.

Отправлять push только если событие действительно важно.

Избегать лишних уведомлений.

---

# Этап 11. Frontend API

Создать REST API.

Все методы должны быть документированы.

Для каждого эндпоинта необходимо:

- описание;
- примеры запросов;
- примеры ответов.

---

# Этап 12. Тестирование

Для каждого нового сервиса необходимо написать:

- Unit Tests;
- Integration Tests.

---

# Этап 13. Документация

После завершения каждой задачи необходимо:

- обновить README;
- обновить архитектурную документацию;
- обновить диаграммы при необходимости.

---

# Требования к коду

Каждый новый модуль должен:

- иметь понятную структуру;
- содержать комментарии только там, где это действительно необходимо;
- быть независимым;
- быть покрытым тестами;
- использовать интерфейсы вместо жёстких зависимостей;
- не содержать дублирования кода.

---

# Главный принцип проекта

Не писать код "лишь бы работало".

Каждое архитектурное решение должно учитывать дальнейшее масштабирование проекта до миллионов пользователей.
